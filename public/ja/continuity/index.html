What if…

Continuity

長期委任を検討する人が気になるシナリオへの率直な回答: 運用者不在 / 鍵紛失 / ネットワーク event / web 障害。 何が回収可能で何が不可能か、所要時間はどれくらいか。 保守的に書いてあるので、実際の日はこのページが言うより悪くなることはまずありません。

委任者向け TL;DR

  • Metal Blockchain には slashing がありません。委任 stake が焼失したり没収されたりすることはありません。最悪でも 1 cycle 分の報酬が得られないだけです。
  • cycle 終了時に委任は自動的に解除されます。仮に今日、こちら側のインフラが全部消えても、P-Chain は委任 METAL を予定通り委任者に返却します。validator 本体の存在は必要条件ではありません。
  • self-stake 回収は運用者側の責任。運用者の鍵紛失が委任者の資金に影響することはありません。
  • 状態は誰でも独立検証可能。このサイトが落ちていても、api.metalblockchain.org に直接問い合わせれば同じデータが取れます。中間者なし。

validator 側のシナリオ

metalgo プロセスのクラッシュ / VM 再起動

対応済。metalgo は systemd の Restart=on-failure で起動、ホスト再起動後 90 秒以内に validator が再稼働します。P-Chain 上の uptime% が落ちるのは、十分な数の peer が一定時間以上の downtime を観測 + 合意投票が動いた場合のみなので、一発の再起動は public 数値上はほぼ見えません。

ハードウェア / ホスティング provider 障害

validator は validator host production-grade VPS で稼働しています。数分以上の validator host リージョン障害は uptime% に観測可能な凹みとして現れます。self-stake と累積報酬は影響を受けません — ホストが復帰すれば validator は再接続します。永続的な障害(provider 側のデータ消失)は staker key バックアップから復旧可能(下記運用者セクション参照)。

disk 満杯 / RAM 圧迫 / peer 数崩壊

常時監視。別系統のアラートパイプライン(ntfy → 運用者の端末)が disk > 85% / RAM > 90% / peer 数 < ~50 / metalgo プロセス消失で発火します。多くの event は public uptime% が気付く前に解消されます。

運用者側のシナリオ

cycle クローズ時に運用者が不在

再登録 tx は期間終了の 2 日前に投入する運用です。運用者が tx を投入できなくなれば、validator は endTime で素直に失効します。self-stake と未請求報酬は運用者の P-Chain アドレスに戻ります。その cycle にあった委任は自動的に各委任者に返却されます — 運用者のアクション不要。validator は運用者が動けるようになってから新規 AddPermissionlessValidatorTx で再登録するか、もしくは二度と再登録しないかは自由です。不在によって何かが破壊されることはありません。

staker key の紛失 / 漏洩

BLS staker key は 3 箇所に backup され、うち 2 箇所は運用者から地理的に分離されています。3 箇所全てを失った場合は、次の期間境界で validator が恒久的に inactive になりますが、対応する self-stake は P-Chain 上で reward address に返却されます(reward address の鍵管理は staker key とは独立した別系統です)。staker key の漏洩で資金が動かされることはなく、最悪でも期間終了まで node identity の impersonation が可能になるだけです。

reward address(wallet)の鍵紛失

self-stake が回収不能になる唯一のシナリオです。reward address は Metal Wallet web 版 wallet(24 語 Avalanche 派生)で、seed は staker key とは別のオフライン媒体に保管されています。両者は同じ媒体に同居しません。

ネットワーク側のシナリオ

Metal Blockchain の hard fork / アップグレード

Metallicus の canonical 指示に従います — validator は Foundation が mainnet 用に publish したバージョンを動かします。fork は事前に upgrade window つきで signal されるので、その window 内、もしくはやむを得ず downtime が発生する場合は window 後にアップグレードします。uptime% への影響は incident log に記録、次の cycle journal entry にも反映されます。

P-Chain の halt / 合意異常

運用者の制御外。監視はしていますが、対応は他の validator と同じ — Metallicus / Metal Foundation の canonical 指示を待ち、指示通りに remediation を適用します。halt 中に運用者側で取れる特別なアクションはありません。

subnet への validation 参加

Phase 1 は mainnet のみです。subnet 参加は roadmap で事前告知し、journal で経緯を説明してから tx を投入する deliberate な判断です。subnet 参加が既存 mainnet 委任に影響することはありません。

Web / 透明性側のシナリオ

このサイトが落ちている時

Web ホスト(web host)と validator ホスト(validator host)は完全に独立しています。web 障害は validator にゼロ影響です。障害中も、誰でも api.metalblockchain.org を直接叩けば本サイトと同じ validator state が取得できます — 具体的な RPC method / filter は 公開データ ページ参照。

domain 失効 / DNS 侵害

domain 更新は失効よりかなり前に autopay で更新されます。状態は運用者の月次レビューチェックリスト項目です。validator は on-chain で存在しているので、domain は表示レイヤーに過ぎません。metal.freedom-yield.com が resolve しなくなっても、NodeID は引き続きブロックを validate し続け、public dashboard だけが見えなくなります。

結論

Avalanche 派生チェーン(Metal を含む)は、運用者が悪意ある行動をしても、姿を消しても、委任者の資金は安全に 設計されています。P-Chain は委任 stake を予定通り返却し、委任者の元本に害を及ぼす slashing は存在しません。 「Freedom Yield が明日消える」シナリオの最悪結果でも、1 cycle 分の報酬を取り損ねるだけ — 今の運用ペースでは 約 1 ヶ月分です。

その protocol-level の安全に加えて当方が上乗せするもの: 公開された監査トレース(incidents / journal / open data)、 3 箇所の独立 backup を持つ documented な recovery model、そして委任者に影響する判断は実行前に告知する明示的なコミット(事後告知はしない)。
