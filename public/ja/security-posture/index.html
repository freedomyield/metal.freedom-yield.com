多層防御

公開 web 側は外側から 4 つの層で保護される。 具体的な threshold や provider の詳細は公開せず、 運用者側 documentation 内で管理する。 ここでは評価者が typically 必要とする categorical な形だけを示す。

Edge 層(CDN)
常時 L3 / L4 DDoS 自動緩和、 IP reputation filtering、 静的 asset の edge cache、 HTTPS 終端。 IP 単位の rate limiting も本層で active。 攻撃継続時の rule 強化手順は docs/SECURITY_LAYERS.md の runbook 参照。
Application gateway
Caddy reverse proxy が IP / endpoint 単位の quota を in-memory で enforce。 quota 超過は 429 Too Many Requests。 edge CDN forwarded IP を honour する設定。
Host network
web host 側 provider-managed firewall と TLS terminator が edge と application gateway の間に挟まる。 上流層で吸収しきれない攻撃には provider-side DDoS 緩和を escalation channel として利用可。
OS / SSH
標準 hardening。 validator 側で標準 web / SSH ポートのみを host firewall で開放、 両 host で SSH daemon に fail2ban、 SSH は公開鍵のみ(password 認証無効)。 運用者 dashboard は認証背後、 password 由来 credential は high-cost hash で保管。

具体的な rule 数値、 ポート allowlist、 blocklist source、 認証 credential の保管 path は SECRET / CONFIDENTIAL(下記)に分類され、 本ページには意図的に出さない。

Validator key の取り扱い

validator は metalgo で稼働し、 その staking dir 配下の 3 file が identity と signing の中核。 私有部分の repository commit は constitution で禁止(CONSTITUTION §3.3)、 .gitignore でも該当拡張子を二重に block する。

staker.crt
公開 X.509 証明書。 hash が NodeID の元。 公開可、 explorer に出る。
staker.key
staking 私鍵。 host の暗号化 volume 外には絶対に出ない。 SECRET 分類(S1)。
signer.key
BLS 署名私鍵。 staker.key と同じ扱い。

backup は off-host で暗号化保管し、 独立した複数 location に置く。 full path を公開 artifact に書くことはない。 rotation 戦略は Avalanche 由来の制約(active な validation 期間中に key 差し替えると NodeID が変わって stake 無効化)に従い、 cycle 境界に合わせる。 漏洩対応手順(ノード停止 → 該当 backup の特定と破棄 → 新 NodeID 立ち上げ → incident entry 公開)は runbook に文書化済。

Avalanche 派生 P-Chain には validator 側不正動作に対する slashing がない。 active 期間中に staker.key を盗まれた場合の最悪影響は逸失利益の window であって、 運用者 / 委任者の元本毀損ではない。

完全な backup 手順、 on-disk path、 暗号化 tooling の specifics、 運用者 workstation 上の key 配置は SECRET 分類で、 運用者側 runbook にのみ存在する。

情報分類

本 validator に紐づく item は Constitution §4 定義の 3 階層のいずれかに必ず属する。 分類不明瞭な item は、 より制限的な扱いを適用する(decision rule)。

SECRET
開示により validator の攻撃可能性 / 可操作性が変わる item: validator 私鍵、 全 wallet seed と passphrase、 運用者 dashboard credential、 SSH credential と key path、 具体的 host IP / hostname、 ntfy topic 識別子、 third-party API token 等。 公開 surface に一切現れない。
CONFIDENTIAL
bearer secret ではないが、 開示が攻撃面 / 運用予測可能性を形作る item: 役割別 cloud provider 名、 hardware 仕様詳細、 監視 tool 名、 on-call 時間帯、 運用者管理 path 配下の内部 directory 構造等。 default は do-not-publish、 categorical reference は許容。
PUBLIC
brand 名、 NodeID と Proof of Possession、 self-stake 額、 fee、 委任者数、 cycle 関連 tx ID、 管轄(国レベル)、 公開 site endpoint、 categorical な architecture 言及(two-host 分離、 自動 deploy、 監視 discipline)。

decision rule、 階層別の完全な item list、 reclassification 手続きは Constitution に詳述。 実務上もっとも重要な rule は上記の「迷ったら制限的扱い」 のみ。

脆弱性報告

repo の top-level SECURITY.md に報告 channel と coordinated disclosure policy を記載:

Channel
bp@freedom-yield.com 宛 email。 公開 GitHub issue は明示的に脆弱性報告の channel ではない。
Acknowledgement target
日本の営業日ベースで 48 時間以内。
Triage target
7 日以内に severity assessment と指標的 fix timeline を返す。
Disclosure model
default 90 日 embargo の coordinated disclosure。 上流調整が必要な場合は相互合意で延長可。

In scope: 本 repo の code / 構成、 production deploy、 本 site に NodeID 掲載済の validator 自体。 Out of scope: 上流 metalgo(MetalBlockchain/metalgo に直接報告)、 edge / host provider の問題(各 vendor 直接)、 単純 traffic flood DoS(edge 層で吸収)、 影響実証なしの best practice 提案。

本ページが「ではない」もの

本ページは運用者の自己適用 discipline を要約したもの。 SOC 2 attestation でも、 何らかの規制 framework 下の certification でも、 契約上のセキュリティ保証でもない。 運用者は規制 accreditation を主張しない。 公開する verifiable artifact を、 評価者が自身の framework に入力する材料として提供するに留まる。

本ページは exhaustive でもない。 具体的な defense threshold、 完全な運用者側手順、 CONFIDENTIAL infrastructure 詳細は意図的に公開 web から外す。 個別のより深い詳細が bilateral に必要な評価者は 問い合わせ surface から連絡可能 — 該当 item は分類に応じた confidentiality 姿勢で議論する。
