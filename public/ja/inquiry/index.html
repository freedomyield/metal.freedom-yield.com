送信手段

email を info@metal.freedom-yield.com 宛に送信。 Web form なし、 third-party tracking なし、 氏名・所属の必須項目なし。 throwaway address でも OK、 返信不要なら返信用 identifier 無しの質問でも OK。

公開鍵暗号 mail は歓迎しますが必須ではありません。 PGP key が必要なら 1 行目に request すれば、 運用者が現在の key fingerprint と ID を返信します。

応答 target

運用者は 日本の営業日(週末・日本の祝日を除く)ベースで 24 時間以内の初回応答 を target とします。 これは運用者の unilateral commitments の 1 つ(commitment #10)です。

初回応答は質問への実質的な回答か、 明確な bilateral 次ステップの提示のいずれか。 「受領しました、 後で返します」 1 行で済ませることを target としません。 簡単な質問には答えそのものが返り、 運用者が今日時点で context を持たない質問には次の 2 ステップが返ります。

SLA ではありません。 24 時間 target は goodwill commitment であり contractual 義務ではありません。 validator 自身に対する incident-response 義務が問い合わせ応答より優先します。

時間 sensitive な事項の速い経路

観測可能な validator state に関する事項(= uptime tick の欠落、 C → P 転送の遅延、 想定外の delegation、 explorer 上の anomaly 等)については、 運用者に連絡せずに済む最速 signal channel が既にあります:

  • explorer.metalblockchain.org — on-chain の canonical source。 email round-trip より速い。
  • /ja/journal/ では、稼働履歴、validation transaction、explorer 参照を含む cycle 単位の運用記録を公開しています。/api/validator.json は現在の validator 状態を machine-readable 形式で提供します。/peers/ はアクセス制限された operator 向け表示です。

再現可能な public anomaly だが validator outage ではない事項(= 公開 artifact の schema 違反、 documentation の defect、 clean machine で再現しない verification recipe 等)については、 GitHub issue を開くほうが email より bandwidth が高い ── public に残り、 comment が累積し、 運用者の応答も同じく public に観測される。

escalation は意図的に single-tier。 on-call rota も pager tier も secondary contact も無い。 validator-host integrity は info@ と独立した自動 alert で監視されており、 incoming inquiry が本物の outage の第一報になることはない。

本 surface の適切な質問

運用者が本 validator surface で意味のある回答ができる質問:

  • 運用者の commitments や リスク開示 に対する due diligence
  • 適性スコアカード や リファレンスアーキテクチャ の明確化
  • Cycle 履歴、 uptime methodology、 /api/uptime-cycles.json の特定 row の意味についての確認
  • Subnet pilot bilateral 協議(/ja/subnet-pilot/ 参照)
  • 公開情報を超える、 運用者側からの回答を要する compliance / regulatory 質問
  • 公開 artifact のバグ報告(broken link, schema drift, 事実誤認)

初回メッセージに含めると有用な情報

以下のいずれかが初回 message に含まれていると、 運用者が清算質問を投げ返さず完全な初回応答を返せます:

連絡の背景
評価コンテキストか具体的ニーズを 1 文。「X 用候補としてこの validator を見ている」 で十分、 X が回答の形を決めます。
質問の起点となった artifact
該当 page URL や API endpoint。 運用者が問われている field / 主張を即時に引ける。
そちらの制約条件
管轄、 規制フレームワーク、 タイムゾーン、 意思決定タイムライン。 開示可能な範囲のみ。 出せないものは省略してください。
返信方法
返信先アドレス、 PGP encrypted 必須か、 初回往復後に別チャネルに移すか。

いずれも必須ではありません。 1 行の質問でも OK。

本ページが「ではない」もの

本ページは sales channel、 marketing intake、 採用窓口、 on-chain record の代替、 のいずれでもありません。 明らかに自動化された問い合わせ、 bulk message、 本 validator 運用と無関係なものは応答なく drop されます。 運用者は retail outreach をしない(commitment #7)立場で、 retail-style channel からの inbound も同じ扱いです。

問い合わせデータの取扱い

本問い合わせ経路は plain email です。 web form なし、 third-party tracking なし、 名前 / 所属の入力欄なし、 受信メールサーバの標準配送メタデータ以外の自動 logging はありません。 運用者は問い合わせ内容を CRM / marketing automation / analytics system に取り込みません。 通信中の機密性が必要な場合は PGP を request 可能です。

受信メッセージは bilateral 対話が active な期間 + 合理的なアーカイブ期間 (= 運用者の通常 mail retention、 contractual SLA 不適用なので公表 retention policy としていない) 運用者の mail store に保管されます。 送信者からの削除要求は初回要請時に reasonable に honor します。 運用者は派生的なビジネス用途のためにメッセージを保持しません。

検証可能 evidence の観点では inquiry channel は relevant ではありません — on-chain record / 署名済 identity manifest / public schema + API が canonical な evidence 面です。 email は補完物であり代替ではありません。
