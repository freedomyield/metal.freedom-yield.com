運用の組み立て方

リファレンスアーキテクチャ

小規模な validator は小さく作るべきです。本ページでは、Freedom Yield が現在稼働している トポロジ・データフロー・運用原則を記述します。目的は二つ — 評価者に技術的な一次資料を提供すること、 そして他の小規模運用者が参考にできるパターンを文書化すること。具体的なプロバイダ・IP・ホストパス は 意図的に開示しません。価値はパターンそのものにあります。

2 ホストトポロジ

本運用は 2 つの分離された商用 VPS インスタンス上で稼働しています。それぞれ役割・到達性プロファイル・障害時の影響範囲が異なります。

トポロジ図 
┌────────────────────────────────┐        ┌───────────────────────────────┐
│  Validator host  (APAC region) │        │  Web host  (Japan region)     │
│                                │        │                               │
│  metalgo (Metal mainnet)       │        │  Caddy (HTTPS, CSP)           │
│  cron-based monitoring         │        │  Static public site           │
│  retry-with-backoff push       │        │  /api/*.json from validator   │
│                                │        │                               │
│  inbound: 9651 (peers only)    │        │  inbound: 80/443 (public)     │
│  outbound: → web host (push)   │        │  inbound: 22 (operator only)  │
└────────────────┬───────────────┘        └────────────────▲──────────────┘
                 │                                         │
                 │  one-way push (forced-command wrapper)  │
                 └─────────────────────────────────────────┘

2 つのホストはサイジングが異なります。Validator host は単一ネットワークの metalgo ワークロード + 十分なマージン用にサイジング、 Web host は静的配信 + validator host から書き込まれる小サイズの JSON ファイル用にサイジング。

なぜ 2 ホストに分けたのか

この分離は本構成における最も重大なアーキテクチャ判断であり、機能追加よりも先に存在します。理由は 3 つ:

  1. Validator uptime が KPI — web 側障害(DDoS、CDN 問題、web サーバクラッシュ)が metalgo のコンセンサスシグナルに影響してはいけません。公開サイトを同一マシン上でホストすると両者が結合します。分離すれば結合は切れます。
  2. 攻撃面の分離 — Validator host が公開インターネットに出すのは P2P トラフィックのみ。SSH は世界の大部分に対して閉じており、 web トラフィックは全く配信しません。Web host は 80/443 を出す明らかなターゲットですが、 そこが侵害されても validator の鍵材料には到達しません。
  3. 容量の隔離 — 公開サイト側のトラフィックスパイクが metalgo から CPU を奪うことはありません。Subnet 拡張が公開サイトの容量を奪うこともありません。

Validator host の役割

  • metalgo が P2P ポートに bind。Staking key はローカルに保管され、他プロセスから読まれることはない。
  • Cron 駆動のヘルスチェックを短い間隔で実施: peer 数・validator 状態・disk pressure・log 異常。
  • Cron 駆動のデータ生成: validator state・peer 地理情報・uptime 履歴・fee-market サマリ・cycle ledger。出力は小さい JSON / JSONL で atomic に書き込み。
  • 専用 SSH key と forced-command wrapper で web host への outbound-only push。Wrapper はファイル名を allowlist で検証してから atomic mv。
  • Web host の SSH ポートは恒常的な brute-force ノイズに晒されており、 正当な push が偶発的に random-drop に巻き込まれることがあります。Retry-with-backoff(短い再試行 2 回 + 指数バックオフ)で観測された失敗率をカバー。
  • ローカルの append-only 永続化ストリーム(JSONL): uptime・gini・peer 変化・fee market・node health。これらが長期 audit trail のソース。

Validator host 側の runbook は公開リポジトリにあります:

  • docs/DISASTER_RECOVERY.md
  • docs/KEY_ROTATION.md
  • docs/VALIDATOR_RENEWAL.md
  • docs/INCIDENT_RESPONSE.md

Web host の役割

  • Caddy が静的サイトを配信。自動 HTTPS・HSTS・厳格な Content-Security-Policy(default-src 'none' をベースに各 directive ごとに narrow allowlist)。
  • Web フレームワークなし、アプリケーションサーバなし、DB なし — 面積は意図的に最小化。
  • /api/* の公開 JSON エンドポイントは validator host の push wrapper によって書き込まれます。Web host は validator key 材料を持たず、 validator data を自前で生成することはできません。
  • GitHub Actions が SSH + rsync で site shell の変更を反映。Deploy の rsync は --delete を使うため、 runtime 生成の API feed が消されないよう個別ファイルの exclude list を維持しています。

片方向のデータフロー

全てのデータは validator host から web host に流れます。Web host から validator host への read access はありません。Push チャネルは以下を使用:

  • 専用 ed25519 SSH key、 wrapper を起動する以外の権限なし。
  • Web host 側の forced-command wrapper がファイル名を allowlist で検証(固有ファイル名 + hex-token .ics パターン)。
  • 受信時に JSON を検証、 atomic mv で公開 web root に配置。
  • Strict host key checking — StrictHostKeyChecking=no は使用しない。

Push key が侵害されても、 攻撃者は allowlist にマッチするファイル名で、 特定 destination ディレクトリに、 wrapper の content-type チェック通過後にしか書き込めません。横移動は不可能です。

鍵の分離

3 種類の鍵カテゴリ、 それぞれ別の場所で別の理由で保管:

Validator staking + BLS 鍵
Validator host にのみ保管。Rotation runbook に従いホスト外に暗号化バックアップ。コンセンサス用にのみ metalgo が使用。
Operator identity 鍵
専用 ed25519、 operator の local ワークステーションにのみ保管。ssh-keygen -Y で off-chain identity manifest を署名するために使用。Validator host・web host のいずれにも置きません。スキーマと検証手順は /api/identity.example.json + docs/IDENTITY_VERIFICATION.md に記載。
Push 鍵
Validator host → web host、 ed25519、 forced-command wrapper にスコープ。Wrapper の allowlist から逸脱不可。

Validator の signing key を off-chain 署名や外部認証に再利用することはありません。これは絶対遵守 — 運用上の署名対象ごとに、 その用途専用の鍵を用意します。

監視・アラート・永続化

  • Cron ベースのスケジュールチェックを短い間隔で実施。失敗は operator にモバイル push 通知。
  • Append-only 永続化ストリーム(JSONL): uptime サンプル・gini 履歴・peer 変化・fee market 履歴・node-health サンプル を記録。これらが長期 audit trail。
  • Daily digest 通知が wallet 残高・peer 数・cycle ヘルスをサマリ送信。14 日 retention で通知ノイズを抑制。
  • 外部 API 呼び出し(RPC・explorer)は数分〜数十分の TTL キャッシュを使用 — Cron 頻度 ≠ API 呼び出し頻度。

本ページが「ではない」もの

本ページはコピー&ペースト可能なデプロイガイド、 完全な config ダンプ、 他運用者に同じプロバイダや同じ仕様を採用するよう推奨する文書、 すべての runbook の網羅記述、 のいずれでもありません。 構造上のリファレンス — 原則・トポロジ・ホスト間 invariant — を示すものです。 具体的なプロバイダ・IP・ホスト名・ポート・パス・認証情報は本サーフェスには意図的に載せていません。 類似パターンを採用する運用者は、 fresh な脅威モデルに基づき独自に判断してください。

third-party 依存

本番運用は以下の外部サービスに依存しています。 各行は目的、 third-party が access できるデータ、 その third-party が停止した場合の影響、 代替経路を記録します。 構造上、 いずれの third-party も operator の鍵材料 custody を持たない設計です。

サービス目的データ access障害影響代替
Validator host プロバイダ 単一テナント VPS 上で metalgo を hosting 標準的なインフラ access のみ。 動作プロセスとその state ディレクトリ以外の operator データはなし backup から代替ホストに復旧するまで validator はオフライン provider firewall + 固定 IPv4 を提供する Linux VPS であれば任意の IaaS。 docs/VALIDATOR_HOST_SETUP.md 参照。
Web host プロバイダ 静的サイトと push wrapper が書き込む runtime JSON endpoint を hosting 静的ファイル + push wrapper のみ。 operator の secret 材料・validator 鍵材料は一切なし 公開検証 surface が unavailable。 validator には影響なし 静的配信と SSH ベースの rsync 受け取りに対応する任意の商用ホスト。 docs/DEPLOY_SETUP.md 参照。
CDN / edge プロキシ Edge cache、 DNS hosting、 baseline DDoS 緩和、 edge での HTTPS 終端 公開 HTTP トラフィックに対する標準的な reverse-proxy ロール Edge cache が degraded、 origin から直接配信は継続 reverse-proxy と DNS hosting に対応する任意の CDN。 現状の設定判断とその根拠は docs/CF_POLICY.md に記載。
Git hosting + CI 公開ソースリポジトリ + サイトシェル変更の CI 駆動 deploy 公開ソースコードのみ。 web host への deploy SSH key は CI 側で repository secret として保持 Deploy 停止。 operator workstation からの手動 rsync は引き続き利用可能 SSH ベースの deploy key と Actions 相当の runner をサポートする任意の git ホスト。
Upstream Metal RPC endpoint データフィード cron が使用する network state クエリ (peer list、 fee market、 validator set) 公開 on-chain クエリのみ。 鍵材料は送信しない Live network 観測フィードが degraded、 validator のコンセンサスパスには影響なし 到達可能な任意の Metal RPC peer。 upstream 消費先は docs/EVIDENCE_MANIFEST.md に記載。
Upstream Metal explorer cross-verification のための block + transaction 参照 (anchor receipt、 AddValidator transaction) 公開 on-chain クエリのみ 訪問者にとって anchor-receipt の cross-check リンクが切れる。 on-chain raw データ自体は他 explorer や直接 RPC 経由で参照可能 任意の Metal explorer インスタンス。
push 通知サービス 監視イベントと daily digest 用の operator-side アラート operator-side のみ。 delegator・訪問者のデータなし。 アラート本文には運用サマリのみ operator のインシデント検知が遅れる。 visible state とインシデントログには影響なし topic-based publish API を持つ任意の push 通知サービス。 substitution パターンは TOOLKIT.md に記載。
operator パスワードマネージャ operator-side の secret 保管 (backup passphrase、 カレンダー token、 dashboard 認証情報) operator-side のみ operator-side の復旧が手動になる。 公開 surface には影響なし offline export 可能な任意のパスワードマネージャ。
ドメインレジストラ 公開ドメインの DNS 委任権限 なし (公開された registration 情報のみ) registrar 側で復旧するまで DNS 解決失敗 任意の ICANN 認定レジストラ。

operator の鍵材料・delegator 資金・validator-signing 材料を custody する third-party は一つもありません。 上記各行には少なくとも 1 つの substitution 経路が記録されており、 トポロジは「validator host 以外の単一依存を失っても、 劣化するのは公開検証 surface であり validator 自体ではない」 という設計です。
