How the operation is built

Reference architecture

A small validator should be small. This page describes the topology, data flow, and operational principles behind Freedom Yield as it runs today. The intent is twofold: give an evaluator a single technical reference, and document a pattern that another small operator could adopt. Specific providers, IPs, and host paths are intentionally not disclosed; the pattern is the value.

Two-host topology

The operation runs on two segregated commercial VPS instances. They have different roles, different reachability profiles, and different failure consequences.

Topology diagram 
┌────────────────────────────────┐        ┌───────────────────────────────┐
│  Validator host  (APAC region) │        │  Web host  (Japan region)     │
│                                │        │                               │
│  metalgo (Metal mainnet)       │        │  Caddy (HTTPS, CSP)           │
│  cron-based monitoring         │        │  Static public site           │
│  retry-with-backoff push       │        │  /api/*.json from validator   │
│                                │        │                               │
│  inbound: 9651 (peers only)    │        │  inbound: 80/443 (public)     │
│  outbound: → web host (push)   │        │  inbound: 22 (operator only)  │
└────────────────┬───────────────┘        └────────────────▲──────────────┘
                 │                                         │
                 │  one-way push (forced-command wrapper)  │
                 └─────────────────────────────────────────┘

The two hosts are sized differently. The validator host is sized for a single-network metalgo workload with comfortable margin. The web host is sized for static serving plus the small JSON files that the validator host writes to it.

Why two hosts

The split is the single most consequential architectural decision in this setup, and it predates any feature work. Three reasons:

  1. Validator uptime is the KPI. A web outage — DDoS, CDN issue, web-server crash — must not affect metalgo consensus signals. Hosting the public site on the same machine couples them; segregating them decouples them.
  2. Attack surface separation. The validator host exposes only peer-to-peer traffic to the public internet. SSH is closed to most of the world; web traffic is not served at all. The web host exposes 80/443 and is the obvious target — but a compromise there does not yield any validator key material.
  3. Capacity isolation. A spike in public-site traffic does not steal CPU from metalgo. A subnet expansion does not steal capacity from the public site.

Validator host role

  • metalgo binding to peer-to-peer port; staking keys held locally and never read by any other process.
  • Cron-driven health checks at small intervals: peer count, validator status, disk pressure, log anomalies.
  • Cron-driven data generation: validator state, peer geography, uptime history, fee-market summary, cycle ledger. Output is small JSON / JSONL, written atomically.
  • Outbound-only push to the web host using a dedicated SSH key bound to a single command (forced-command wrapper). The wrapper validates filename against an allowlist before atomic mv.
  • Push uses retry-with-backoff because the web host's SSH port sees constant brute-force noise; legitimate pushes occasionally lose to the random-drop logic. Two retries with backoff cover the observed failure rate.
  • Local persistence streams (append-only JSONL) for uptime, gini, peer changes, fee market, node health. These are the source of truth that the web host mirrors.

Web host role

  • Caddy serves the static site with automatic HTTPS, HSTS, and a strict Content-Security-Policy (default-src 'none' base, narrow allowlists per directive).
  • No web framework, no application server, no database — the surface is intentionally tiny.
  • Public JSON endpoints under /api/* are written by the validator host's push wrapper. The web host has no validator key material and cannot generate validator data itself.
  • GitHub Actions ships site-shell changes via SSH + rsync. The deploy rsync uses --delete with an explicit per-file exclude list for runtime-generated API feeds, so cron-pushed data is not wiped on deploys.

One-way data flow

All data flows from the validator host to the web host. The web host has no read access to the validator host. The push channel uses:

  • A dedicated ed25519 SSH key with no privileges beyond invoking the wrapper.
  • A forced-command wrapper on the web host that validates filename against an allowlist (specific filenames, plus a hex-token .ics pattern for calendars).
  • JSON validation on receipt before atomic mv into the public web root.
  • Strict host key checking — no StrictHostKeyChecking=no.

If the push key is compromised, the attacker can only write files whose names match the allowlist, into the specific destination directory, after passing the wrapper's content-type check. They cannot pivot.

Key separation

Three distinct key categories, each held in a different place for a different reason:

Validator staking + BLS keys
Held only on the validator host. Encrypted backups maintained off-host per the rotation runbook. Used only by metalgo for consensus.
Operator identity key
Dedicated ed25519, held only on the operator's local workstation. Used to sign the off-chain identity manifest via ssh-keygen -Y. Never on validator or web host. Schema and verification procedure are documented at /api/identity.example.json + docs/IDENTITY_VERIFICATION.md.
Push key
Validator host → web host, ed25519, scoped to the forced-command wrapper. Cannot escape the wrapper's allowlist.

The validator's signing keys are never reused for off-chain signing or external authentication. This is a hard rule: every operational signing concern uses a key dedicated to that concern.

Monitoring, alerting, persistence

  • Cron-based scheduled checks at small intervals; failures are pushed to the operator via mobile push notification.
  • Append-only persistence streams (JSONL) record uptime samples, gini history, peer changes, fee-market history, node-health samples. These are the long-horizon audit trail.
  • Daily digest notifications summarise wallet balances, peer count, and cycle health. The 14-day retention window keeps notification noise bounded.
  • External API calls (RPC, explorer) use TTL caches measured in minutes-to-tens-of-minutes — cron frequency is not API-call frequency.

What this page is not

This is not a copy-pasteable deployment guide, a complete configuration dump, a recommendation that another operator adopt the same providers or specs, or an exhaustive description of every runbook. It is a structural reference: the principles, the topology, and the cross-host invariants. Specific providers, IPs, hostnames, ports, paths, and credentials are intentionally absent from this surface; an operator deciding to follow a similar pattern should make those choices independently from a fresh threat model.
