Reaching the operator

Inquiry

How to reach the operator of this validator, what kind of question is appropriate at this surface, and what to expect in terms of response time. There is no required identifier — an anonymous question is fine — and there is no form gating the inquiry behind javascript or third-party services.

How to send an inquiry

Send email to info@metal.freedom-yield.com. No web form. No third-party tracking. No required name or organisation. A throwaway address is fine; a question with no return identifier is fine if you do not need a reply.

Public-key encrypted mail is welcome but not required. If you need a PGP key, request one in the first plaintext line and the operator will reply with the current key fingerprint and ID.

Response target

The operator targets a 24-hour first response on Japan business days (excluding weekends and Japanese national holidays). This is one of the operator's unilateral commitments (commitment #10).

The first response either substantively answers the question or sets a clear bilateral next step. A single line saying "received, will get back to you" is not the target. If the question is straightforward, the response is the answer; if the question needs context the operator does not have today, the response is the next two steps.

There is no SLA. The 24-hour target is a goodwill commitment, not a contractual obligation. The operator's incident-response duties to the validator itself take precedence over any inquiry.

Faster paths for time-sensitive matters

For matters relating to observable validator state (= a missed uptime tick, a slow C → P transfer, an unexpected delegation, an explorer anomaly), the fastest signal channels do not require contacting the operator at all:

  • explorer.metalblockchain.org — the canonical on-chain source. Faster than any email round-trip.
  • /journal/ provides the public per-cycle operational record, including uptime history, validation transactions, and explorer references. /api/validator.json provides the current machine-readable validator state. /peers/ is a restricted operator view.

For matters that are reproducible public anomalies but not validator-state outages (= a schema break in a published artifact, a documentation defect, a verification recipe that does not reproduce on a clean machine), opening a GitHub issue is higher-bandwidth than email — it stays public, accumulates comments, and the operator's response is also publicly observable.

Escalation is single-tier by design: there is no on-call rota, no paging tier, no secondary contact. Validator-host integrity is monitored by automated alerts independent of info@; an incoming inquiry will not be the first signal the operator receives about a real outage.

What this surface is for

Questions where the operator can usefully reply at the validator surface:

  • Due diligence on the operator's commitments or risk disclosures.
  • Clarification on the readiness scorecard or reference architecture.
  • Specifics about cycle history, uptime methodology, or what a particular row in /api/uptime-cycles.json means.
  • Bilateral subnet-pilot conversation (see also /subnet-pilot/).
  • Compliance / regulatory questions that require operator-side answers beyond what is published.
  • Bug reports against the public artefacts (broken link, schema drift, mis-stated fact).

What helps in the first message

Including any of the following in the first message lets the operator return a complete first response instead of a clarifying question:

Why you are reaching out
One sentence describing the evaluation context or the specific need. "Looking at this validator as a candidate for X" is enough; the X helps shape the answer.
What artefact prompted the question
A page URL or an API endpoint, if applicable. Lets the operator pull up the exact field or claim under question.
Constraints you operate under
Jurisdiction, regulatory framework, time-zone, decision timeline. Only what you are comfortable sharing — anything you cannot share, simply omit.
How to reply
Reply-to address; whether the reply must be PGP-encrypted; whether the conversation should move to another channel after the first round.

None of the above is required. A one-line question is also acceptable.

What this page is not

This is not a sales channel, a marketing intake, a recruiting front, or a substitute for the on-chain record. Inquiries that are clearly automated, bulk, or unrelated to the operation of this validator are dropped without response. The operator does not pursue retail outreach (commitment #7) and treats inbound from retail-style channels accordingly.

Inquiry data handling

The inquiry channel is plain email. No web form, no third-party tracking, no required name or organisation, no automated logging beyond what the receiving mail server records as standard delivery metadata. The operator does not import inquiry contents into a CRM, marketing automation, or analytics system. PGP is available on request for messages that need transit confidentiality.

Received messages are retained in the operator's mail store for as long as the bilateral conversation is active and for a reasonable archival window afterwards (= the operator's normal mail retention; not a published retention policy because no contractual SLA applies). Deletion requests by the sender are honored within reason on first ask; the operator does not retain messages for derivative business uses.

For verifiable evidence the inquiry channel is irrelevant — the on-chain record, the signed identity manifest, and the public schemas + APIs are the canonical evidence surface. Email is a complement, not a substitute.
