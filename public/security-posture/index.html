How the operator approaches security

Security posture

A summary of how this validator handles defense in depth, validator key custody, information classification, and vulnerability reporting. This page is a synthesis for evaluators; the underlying public documents in the repository (Constitution, SECURITY_LAYERS, KEY_ROTATION, SECURITY) remain authoritative.

Defense in depth

The public web side is protected in four categorical layers, outermost first. Specific tunings, thresholds, and provider details are kept off the public web and managed in operator-side documentation; what follows is the categorical shape an evaluator typically needs.

Edge layer (CDN)
Always-on L3 / L4 DDoS auto-mitigation, IP reputation filtering, edge caching for static assets, HTTPS termination. Per-IP rate limiting active at this layer. Tightening rules exist for sustained attack — see the runbook in docs/SECURITY_LAYERS.md.
Application gateway
A Caddy reverse proxy enforces per-IP and per-endpoint quotas in memory. Requests over quota return 429 Too Many Requests. The plugin honours the edge-CDN-forwarded client IP.
Host network
The web host's own provider-managed firewall and TLS terminator sit between the edge and the application gateway. Provider-side DDoS mitigation is available as an escalation channel if the upstream layers are overwhelmed.
OS / SSH
Standard hardening: a host firewall exposing only standard web and SSH ports on the validator side, fail2ban on the SSH daemon on both sides, public-key SSH only, password-based SSH disabled. Operator dashboards behind authentication; password-derived credentials use a high-cost hash.

Concrete rule numbers, port allowlists, blocklist sources, and authentication credential storage paths are classified SECRET or CONFIDENTIAL (see below) and intentionally not exposed on this page.

Validator key handling

The validator runs metalgo; three files in its staking directory drive identity and signing. The constitution forbids ever committing the private parts to the repository in any form (CONSTITUTION §3.3), and the .gitignore blocks the relevant extensions as a second line of defense.

staker.crt
Public X.509 certificate. Its hash is the source of the NodeID. Publishable; appears in the explorer.
staker.key
Private staking key. Never leaves the host's encrypted volume. Classified SECRET (S1).
signer.key
BLS private signing key. Same treatment as staker.key.

Backups are encrypted off-host, stored in independent locations, and never described by full path in any public artifact. The rotation strategy follows the Avalanche-derived constraint that an active validation period cannot have its underlying key swapped without invalidating the NodeID; rotation therefore aligns with cycle boundaries. The compromise-response procedure (stop the node, identify and destroy implicated backups, stand up a new NodeID, publish an incident entry) is documented in the runbook.

The Avalanche-derived P-Chain has no slashing for validator misbehaviour — the worst-case impact of a stolen staker.key during an active period is a window of foregone rewards, not principal loss for the operator or delegators.

Full backup procedure, on-disk paths, encryption tooling specifics, and operator workstation key locations are classified SECRET and live in the operator-side runbook only.

Information classification

Every item connected to this validator falls into one of three tiers defined in Constitution §4. When an item's tier is unclear, the more restrictive treatment is applied.

SECRET
Items whose disclosure changes attackability or operability of the validator: validator private keys, all wallet seeds and passphrases, operator-dashboard credentials, SSH credentials and key paths, specific host IPs and hostnames, ntfy topic identifiers, third-party API tokens. Never appears anywhere public.
CONFIDENTIAL
Items whose disclosure shapes attack surface or operational predictability without being bearer secrets: cloud provider name per role, specific hardware spec, specific monitoring tools, on-call windows, internal directory structure under operator-controlled paths. Default is do-not-publish; aggregate categorical reference is permitted.
PUBLIC
Brand identity, NodeID and Proof of Possession, self-stake amount, fee, delegator count, cycle transaction IDs, jurisdictional country, public site endpoints, architecture statements at the categorical level (two-host separation, automated deploy, monitoring discipline).

The decision rule, the complete item list per tier, and the reclassification process are in the Constitution; the rule that matters most in practice is the one above — when in doubt, treat the item as more restrictive.

Vulnerability reporting

The repository carries a top-level SECURITY.md describing the reporting channel and coordinated disclosure policy:

Channel
Email to bp@freedom-yield.com. Public GitHub issues are explicitly not the channel for vulnerability reports.
Acknowledgement target
Within 48 hours on Japan business days.
Triage target
Within 7 days, with severity assessment and an indicative fix timeline.
Disclosure model
Coordinated disclosure with a default 90-day embargo, extendable by mutual agreement if upstream coordination is required.

In scope: this repository's code and configuration, the production deployment, and the validator itself once its NodeID is on the site. Out of scope: upstream metalgo (report directly to MetalBlockchain/metalgo), edge or host provider issues (report to those vendors), simple traffic-flood DoS (mitigated at the edge), and best-practice suggestions without demonstrable impact.

What this page is not

This page is a summary of operator-applied discipline. It is not a SOC 2 attestation, a certification under any compliance regime, or a contractual security warranty. The operator does not claim regulatory accreditation; the operator publishes verifiable artifacts that an independent evaluator can use as input to their own framework.

The page is also not exhaustive. Specific defense thresholds, complete operator-side procedures, and CONFIDENTIAL infrastructure detail are intentionally absent from the public web. An evaluator who needs deeper detail bilaterally can use the inquiry surface; appropriate items will be discussed under a confidentiality posture matching their classification.
