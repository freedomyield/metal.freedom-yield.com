What if…

Continuity

Plain answers to the scenarios that should worry anyone considering a long-term delegation: operator unavailability, key loss, network events, web outages. What's recoverable, what's not, and the time it takes. Written conservatively — the actual day is rarely worse than the page says.

TL;DR for delegators

  • No slashing on Metal Blockchain. Delegated stake is never burned or seized. Worst case is foregone rewards for one cycle.
  • Delegations unlock automatically when the cycle ends. Even if every piece of infrastructure on our side disappeared today, the P-Chain returns delegated METAL to delegators on schedule. The validator's existence is not required for that.
  • Self-stake recovery is on us, not delegators. Operator key loss affects the operator's own stake only.
  • Status is independently verifiable. If this site is down, query api.metalblockchain.org directly — same data, no middleman.

Validator-side scenarios

metalgo process crash or VM reboot

Handled. metalgo runs under systemd with Restart=on-failure; the host comes back from a reboot to a running validator in under 90 seconds. Uptime% on the P-Chain only ticks down if downtime is reported by enough peers across more than a few minutes of consensus voting, so a one-shot restart is typically invisible in the public number.

Hardware / hosting-provider outage

The validator runs on a validator host production-grade VPS instance. A regional validator host outage of more than a few minutes would show up as a measurable uptime% dip. Self-stake and accrued rewards are unaffected — the validator simply reconnects when the host comes back. Persistent failure (provider-side data loss) is recoverable from staker-key backups; see the operator section below.

Disk fill, RAM pressure, peer count collapse

Monitored continuously. A separate alert pipeline (ntfy → operator phone) fires on disk > 85%, RAM > 90%, peer count < ~50, or metalgo process absence. Most events are resolved before public uptime% would notice.

Operator-side scenarios

Operator is unavailable when a cycle closes

The renewal transaction is filed two days before the period end. If the operator becomes unable to file it, the validator simply expires at endTime. Self-stake and any unclaimed rewards return to the operator's P-Chain address. Active delegations from that cycle return to their delegators automatically — no operator action required. The validator can be re-registered later from a fresh AddPermissionlessValidatorTx once the operator is available again, or never. Nothing is destroyed by absence.

Staker key loss or compromise

The BLS staker key is backed up in three locations, two of which are geographically separated from the operator. Loss of all three would mean the validator becomes permanently inactive at the next period boundary — but the corresponding self-stake on the P-Chain still returns to the reward address (a separate wallet key whose security model is independent). A compromised staker key cannot move funds, only sign blocks; the worst outcome is impersonation of the node identity until period end.

Reward address (wallet) key loss

This is the only failure mode where self-stake could be unrecoverable. The reward address is a Metal Wallet web wallet (24-word mnemonic on the Avalanche derivation), with the seed backed up in a separate offline location from the staker keys. The two key materials never sit on the same medium.

Network-side scenarios

Metal Blockchain hard fork or upgrade

We follow Metallicus' canonical guidance — the validator runs the version the Foundation publishes for the active mainnet. Forks are signalled in advance with a coordinated upgrade window; the validator is upgraded inside that window or, if downtime is unavoidable, after it. Uptime% impact would be documented in the incident log and reflected in the next cycle journal entry.

P-Chain halt or consensus issue

Outside operator control. We monitor for it, but the response is the same as every other validator's: wait for canonical guidance from Metallicus / the Metal Foundation, apply the prescribed remediation. No special operator-side action is possible during the halt itself.

Subnet validation joining

Phase 1 is mainnet-only. Joining a subnet is a deliberate decision that would be announced in the roadmap and explained in the journal before any tx is filed. Subnet participation does not affect existing mainnet delegations.

Web & transparency-side scenarios

This website is down

The web host (web host) and the validator host (validator host) are completely independent. A web outage has zero effect on the validator. During an outage, anyone can query api.metalblockchain.org directly for the same validator state this site displays — see the Open data page for the exact RPC method and filters.

Domain expiration or DNS compromise

Domain renewal is autopay'd well in advance of expiry; status is on the operator's monthly review checklist. The validator's existence is on-chain — the domain is just a presentation layer. If metal.freedom-yield.com ever stops resolving, the NodeID still validates blocks; only the public dashboard goes dark.

The bottom line

Avalanche-derived chains (Metal included) were designed so that delegator funds are safe even when the validator operator behaves badly or vanishes entirely. The P-Chain returns delegated stake on schedule; there is no slashing that could harm a delegator's principal. The worst credible outcome of "Freedom Yield disappears tomorrow" is a single cycle's rewards foregone, which on the operating cadence we run is approximately one calendar month.

What we add on top of that protocol-level safety: a public audit trail (incidents, journal, open data), a documented recovery model with backups in three independent locations, and the explicit commitment that decisions which would affect delegators are announced before they're executed — never after.
